2. Puntos Fuertes ✓

Lo que ya funciona bien. No hay que tocarlo.
  • All in One SEO (AIOSEO v4.9.4.1) instalado y activo: genera title, meta description, canonical, Open Graph y Twitter Card en cada página, además del sitemap dinámico.
  • Title de homepage correcto: "Unique riads and tailor-made tours across Morocco | InMedina.com" — incluye keywords clave (riads, tours, Morocco) y la marca, dentro del límite de Google.
  • Meta description bien dimensionada: ~155 caracteres, con llamada a la acción ("Book now your unique experience") y keywords (Marrakech Medina, private trips, luxury desert camps).
  • Canonical URL correcto y único: 1 sola etiqueta canonical autorreferente en homepage.
  • Sitemap index válido (AIOSEO): sitemap.xml con sub-sitemaps segmentados — listing-sitemap.xml (56 riads), experience-sitemap.xml (31 tours), product-sitemap.xml (21), page-sitemap.xml (35), post-sitemap.xml (4). Catálogo amplio y bien estructurado en taxonomías.
  • robots.txt correcto: Disallow de rutas WooCommerce sensibles (carrito, logs, uploads), Allow de admin-ajax.php, y enlace a los 2 sitemaps.
  • Páginas 404 reales: una URL inexistente devuelve HTTP 404 (no un falso 200, error típico de WordPress mal configurado).
  • Redirect www ➞ non-www correcto: https://www.inmedina.com/ ➞ 301 ➞ https://inmedina.com/. Canonicalización de host bien resuelta (el problema está solo en el redirect HTTP, ver 3.1).
  • Una sola etiqueta H1 en homepage ("Discover Authentic Moroccan Riads & Vacation Rentals") y jerarquía H2 temática coherente (Best Offers, Destinations, Accommodation Type, Excursions, Experiences, Blog).
  • Lazy-load activo: 40 de 63 imágenes con loading="lazy", mejora el LCP en móvil.
  • WhatsApp integrado como canal de contacto/reserva — clave en turismo internacional.
  • HTTPS forzado con certificado válido (sin warnings) y theme de booking dedicado (Homey) con tipos de contenido propios (listing, experience, cancel_policy).

3. Problemas Críticos (4)

Estos puntos cierran la puerta al tráfico turístico internacional, que es justamente el público de InMedina: el sitio es monolingüe, sin Schema rico, sin security headers y con previews sociales rotas. El redirect HTTP mal configurado (3.1) se ha reclasificado como Importante porque solo afecta a peticiones http://, no al usuario con navegador.

3.1 Redirect HTTP ➞ HTTPS mal configurado (pierde el .com) IMPORTANTE

Aclaración importante. En el navegador el sitio se abre perfectamente al teclear inmedina.com: los navegadores modernos (Chrome, Safari, Firefox, Edge) van directos a HTTPS desde 2021, así que nunca tocan la versión http://. El problema solo aparece cuando una petición parte explícitamente de http://. No es un "sitio caído", es un header mal formado con impacto acotado.

Qué pasa: al entrar por http:// (sin S), el servidor emite un Location que pierde el .com. Reproducible en varias rutas:

curl -I http://inmedina.com/ ➞ Location: https://inmedina/ (falta el .com) curl -I http://inmedina.com/riads/ ➞ Location: https://inmedina/riads/ (falta el .com)

La regla de reescritura de Apache está perdiendo el TLD del host. https://inmedina/ no resuelve.

Quién se ve afectado (impacto acotado, no catastrófico):

  • Backlinks históricos en http:// — Google no puede seguir un 301 hacia un host que no resuelve, así que se pierde esa equidad de enlace.
  • Algunos crawlers, link-checkers y unfurlers (previews de enlaces) que prueban http:// primero.
  • Clientes no-navegador (ciertos clientes de email, bots, integraciones).

Quién NO se ve afectado: el usuario normal con navegador moderno — por eso al verificarlo "a mano" el sitio carga bien.

Fix: corregir la regla en Apache (.htaccess o virtual host) para conservar el host completo, y añadir HSTS (ver 3.4) para que el navegador ni intente HTTP. 10 minutos. Snippet en sección 7.1.

# Correcto: http://inmedina.com/... ➞ https://inmedina.com/... # (conservando %{HTTP_HOST}, no reescribiéndolo a "inmedina")

3.2 Sitio monolingüe (solo inglés) en un mercado multi-idioma CRÍTICO

Qué pasa: todo el sitio sirve <html lang="en-US"> y og:locale = en_US. No hay plugin multilingüe (no se detecta WPML, Polylang, TranslatePress ni Weglot), no existen URLs /fr/, /es/, /de/, /it/ y cero etiquetas hreflang en el HTML.

Por qué es crítico: el turismo a Marruecos es, por definición, internacional y multi-idioma, y el viajero busca en su propia lengua. Francia es históricamente el primer mercado emisor hacia Marruecos, seguido de mercado hispano, alemán e italiano. Hoy InMedina solo es visible para quien busca en inglés:

  • "riad marrakech" (FR) — volumen muy alto, mercado #1 hacia Marruecos
  • "riad marrakech" / "viaje a Marruecos" (ES) — mercado emisor relevante
  • "riad marrakesch" (DE) — alto poder adquisitivo, gran gasto medio
  • "riad marrakech" / "tour marocco" (IT)
  • "riads in marrakech" (EN) ← el ÚNICO mercado al que llegas hoy

(Volúmenes exactos a confirmar con Google Keyword Planner; el patrón de mercado es indiscutible.) Estás renunciando a una porción enorme de la demanda — fácilmente el 60-70% del tráfico potencial — en un nicho donde el inglés NO es el idioma dominante de búsqueda.

Fix: instalar Polylang (gratis) o WPML (~99€/año, mejor con WooCommerce/Homey). Prioridad de traducción: FR ➞ ES ➞ DE. URLs en subdirectorio (/fr/, /es/...). Ambos generan hreflang y sitemaps localizados automáticamente.

3.3 Schema.org pobre — sin LodgingBusiness, Product/Offer ni TouristTrip CRÍTICO

Qué pasa: el único Schema presente es genérico — Organization + ContactPoint + ImageObject + SiteNavigationElement. Para un sitio de 56 riads y 31 experiencias en venta, esto es prácticamente nada.

Lo que falta (y debería estar):

  • LodgingBusiness / Hotel en cada ficha de riad, con address, geo (lat+lng), priceRange, amenityFeature[], starRating, aggregateRating + review
  • Product + Offer (price, priceCurrency, availability) en los listings y productos WooCommerce ➞ habilita el rich snippet de precio + estrellas en Google
  • TouristTrip / Trip en cada experiencia/excursión (itinerario, duración, punto de salida)
  • TravelAgency en la homepage (categoría correcta del negocio)
  • FAQPage en páginas de info (visados, mejor época, transporte) ➞ rich snippet que multiplica CTR x2-3
  • BreadcrumbList en páginas internas

Por qué es crítico: sin estos tipos Google no te muestra en los paneles ricos de "Hoteles" y "Cosas que hacer" (Things to do), ni genera las estrellas/precio en el resultado de búsqueda. En un sector tan visual y competitivo, perder el rich snippet es perder clics frente a Booking, Airbnb y agencias que sí lo tienen.

Fix: AIOSEO Pro permite Schema por tipo de contenido; alternativamente Rank Math (gratis) trae nativo Hotel/LocalBusiness/Product. Ver snippets en sección 7.3-7.4.

3.4 Cero security headers HTTP + versión de servidor expuesta CRÍTICO

Qué pasa: la respuesta del servidor no incluye ningún header de seguridad, y revela la versión exacta de software:

curl -I https://inmedina.com/ HTTP/1.1 200 OK Server: Apache/2.4.52 (Ubuntu) ➞ versión + SO expuestos innecesariamente Content-Type: text/html; charset=UTF-8 (sin Strict-Transport-Security / HSTS) (sin X-Frame-Options) (sin X-Content-Type-Options) (sin Referrer-Policy) (sin Permissions-Policy) (sin Content-Security-Policy)

Por qué es crítico:

  • Clickjacking: sin X-Frame-Options, el formulario de reserva/pago de Homey puede embeberse en un sitio fraudulento que capture datos de tarjeta.
  • Downgrade attack: sin HSTS, un atacante en WiFi público de hotel/aeropuerto puede degradar HTTPS➞HTTP en la primera visita — especialmente grave porque el público viaja y usa redes abiertas.
  • MIME sniffing: sin X-Content-Type-Options: nosniff, riesgo XSS vía upload.
  • Reconocimiento: Apache/2.4.52 (Ubuntu) dice al atacante exactamente qué CVEs probar.
  • Google Lighthouse penaliza "Best Practices" (-10 a -15 puntos típico), señal indirecta de calidad.

Fix: añadir los headers al .htaccess + ocultar la firma del servidor (ServerTokens Prod / ServerSignature Off). 10 minutos, coste cero. Ver snippet 7.2.

3.5 Open Graph duplicado y con og:type erróneo — previews sociales rotas CRÍTICO

Qué pasa: la homepage inyecta dos juegos de etiquetas Open Graph en conflicto (2× og:title, 2× og:url, 2× og:type...), probablemente porque AIOSEO y el theme Homey las generan ambos. Además:

  • og:type = "article" en la homepage ➞ debería ser "website" (article es para entradas de blog).
  • og:image apunta a una miniatura pequeña ...-300x200.jpg ➞ los estándares sociales piden 1200×630.

Por qué es crítico: cuando alguien comparte InMedina en WhatsApp, Facebook, Instagram o LinkedIn (canales clave en turismo, boca a boca digital), la preview sale rota o con imagen diminuta y datos contradictorios. Facebook/WhatsApp eligen una de las dos etiquetas de forma impredecible. Cada share fallido es publicidad gratuita desperdiciada y peor CTR social.

Fix: dejar una sola fuente de OG (desactivar OG del theme Homey o de AIOSEO, no ambos), forzar og:type=website en homepage y subir una og:image dedicada 1200×630 (foto de riad + claim). Verificar en el Facebook Sharing Debugger.

4. Problemas Importantes (6)

Incluye el redirect HTTP de la sección 3.1 (reclasificado aquí por impacto acotado) más los 5 siguientes.

4.1 Cero imágenes en WebP — sitio pesado en un nicho muy visual IMPORTANTE

Actual: el 100% de las imágenes son JPEG/PNG; 0 en WebP. En un sitio de riads donde la foto es el principal motor de venta, esto infla el peso de página y empeora el LCP, sobre todo en móvil con conexión de viaje (4G/roaming).

Fix: instalar un plugin de optimización (Imagify, ShortPixel o Converter for Media) que convierta y sirva WebP automáticamente con fallback. Reducción típica de 25-40% de peso sin pérdida visible. Combinar con caché (WP Rocket / LiteSpeed Cache si migran).

4.2 8 imágenes sin atributo alt IMPORTANTE

Actual: de 63 imágenes en homepage, 8 no tienen alt. En turismo, Google Images es una fuente de tráfico real ("riad piscina marrakech", "desert camp merzouga"), y el alt es lo que te posiciona ahí + accesibilidad (WCAG).

Fix: rellenar alt descriptivos con keyword + ubicación ("Riad with rooftop pool in Marrakech Medina"). En WordPress se edita desde la Media Library o el campo alt de cada bloque.

4.3 Blog casi inexistente — sin contenido SEO long-tail IMPORTANTE

Actual: el post-sitemap.xml contiene solo 4 entradas, con lastmod 2025-05-16 (más de un año sin publicar). El blog está, en la práctica, abandonado.

Por qué importa: el viajero investiga durante semanas antes de reservar. Cada guía bien hecha capta tráfico orgánico gratuito y mete el lead en tu funnel:

  • "best time to visit Marrakech" / "meilleure période pour visiter Marrakech"
  • "how many days in Marrakech" / "Marrakech en 3 días"
  • "is it safe to travel to Morocco" / "Marrakesch Reisetipps"
  • "Marrakech to Sahara desert tour 3 days"
  • "what to wear in Marrakech medina"

Fix: reactivar el blog, 2 posts/mes de 1000-1500 palabras, enlazando internamente a riads y experiencias relevantes. Cuando el sitio sea multilingüe, publicar al menos en EN+FR.

4.4 Sin headers de caché ni HSTS — rendimiento y visitas recurrentes IMPORTANTE

Actual: la respuesta no muestra Cache-Control ni Strict-Transport-Security. Sin política de caché explícita, el navegador no reutiliza assets de forma óptima entre páginas (un usuario que compara 5 riads recarga recursos innecesariamente).

Fix: activar caché de página + browser caching de assets estáticos (plugin de caché o reglas Expires en .htaccess) y añadir HSTS (incluido en el snippet 7.2). Mejora directa de PageSpeed y experiencia.

4.5 Meta viewport mal formado — bloquea el zoom IMPORTANTE

Actual: <meta name="viewport" content="width=device-width, initial-scale=1.0, maximum-scale=5.0,"> — con una coma final sobrante y, sobre todo, maximum-scale=5.0.

Problema: limitar el zoom es un anti-patrón de accesibilidad (usuarios con baja visión no pueden ampliar a gusto) que Lighthouse marca en la auditoría de accesibilidad. La coma final es sintaxis sucia.

Fix: <meta name="viewport" content="width=device-width, initial-scale=1.0"> (sin maximum-scale, sin coma final).

7. Código Listo para Copiar

7.1 Arreglar el redirect HTTP➞HTTPS roto — .htaccess raíz

Sustituir la regla actual (que pierde el dominio) por una que conserva el host completo:

<IfModule mod_rewrite.c> RewriteEngine On # Forzar HTTPS conservando el host completo (inmedina.com, no "inmedina") RewriteCond %{HTTPS} off RewriteRule ^(.*)$ https://%{HTTP_HOST}%{REQUEST_URI} [L,R=301] </IfModule>

Verificación posterior obligatoria:

curl -I http://inmedina.com/ # Esperado: Location: https://inmedina.com/ (CON el .com)

7.2 Security headers + ocultar versión — .htaccess raíz

<IfModule mod_headers.c> Header always set Strict-Transport-Security "max-age=31536000; includeSubDomains; preload" Header always set X-Frame-Options "SAMEORIGIN" Header always set X-Content-Type-Options "nosniff" Header always set Referrer-Policy "strict-origin-when-cross-origin" Header always set Permissions-Policy "geolocation=(self), camera=(), microphone=()" Header always unset X-Powered-By </IfModule> # Ocultar firma/versión de Apache (en apache2.conf o conf disponible): ServerTokens Prod ServerSignature Off

9. Conclusiones

InMedina parte de una base sólida: WordPress bien montado, AIOSEO configurado, sitemap segmentado, robots.txt correcto, 404 reales, catálogo amplio (56 riads + 31 experiencias) y un theme de booking dedicado. El producto y la estructura no son el problema.

El problema es de visibilidad, y se concentra en tres frentes muy concretos:

  1. Sitio monolingüe en un mercado multi-idioma: vendes Marruecos a un público internacional pero solo eres visible en inglés. El francés (mercado #1) está completamente fuera. Es el mayor ROI disponible.
